공개 평가 관점

Cofa Probe는 코드와 실행 결과에 더해 AI 협업 기록, 검증 과정, 사후 답변을 살펴봅니다. 공개된 기술·의도·인지 관점을 아래 연습 행동에 적용해 보세요. 실제 응시에서는 받은 도구·시간·제출 안내를 따르세요. Cofa Probe 공식 소개 ↗

기술
과제의 실행 명령으로 결과를 재현하세요. 성공 경로와 실패 경로를 모두 검사하고, 코드 변경을 요구사항과 직접 연결하세요.
의도
작업 단위마다 목표, 변경 범위, 유지할 제약, 완료 조건을 정하세요. 새 정보가 생기면 AI에 준 다음 지시를 그 근거에 맞춰 조정하세요.
인지
내 코드에서 값이 계산되거나 상태가 바뀌는 지점을 짚으세요. 선택한 구조의 이유와 그 구조가 보장하는 범위를 설명하세요.

제한 시간 풀이 전략

아래 시간 배분은 연습실 두 과제에 맞춘 예시입니다. 각 구간이 끝나면 손에 남길 결과를 기준으로 다음 단계로 넘어가세요.

단계35분45분확인할 결과
문제 정의0–5분0–7분함수 계약, 바꾸면 안 되는 동작, 직접 계산한 경계 사례 하나
구현5–19분7–25분기존 진입점에서 실행되는 구현과 작은 단위의 확인 결과
검증19–30분25–39분직접 만든 반례, 전체 테스트 실행 결과, 실패 시 재현과 수정 기록
마무리30–35분39–45분변경 범위 점검, 주요 결정 두 가지, 남은 제약 한 가지
  • 명세를 테스트 문장으로 바꾸세요. 입력, 기대 출력, 근거가 되는 명세를 한 줄로 적으세요. 기대값을 AI나 구현에 묻기 전에 손으로 계산하면 같은 오해가 테스트에도 복제되는 일을 줄일 수 있습니다.
  • 증상이 생긴 지점부터 좁히세요. 재현 입력과 기대값을 고정한 뒤 실패 지점 하나를 수정하고 같은 검사로 다시 확인하세요. 이어서 전체 테스트를 실행해 영향 범위를 보세요.
  • 시간이 부족하면 요구 동작부터 완성하세요. 남은 시간에 가장 위험한 미검증 규칙을 하나 고르고 작은 입력으로 확인하세요. 변경 목록과 실행 결과를 제출 전에 확인할 시간을 남기세요.

단계별 프롬프트

프롬프트를 복사해 VS Code에서 쓰는 AI 채팅에 붙여넣으세요. 대괄호 안은 실제 파일명, 명세 문장, 실행 결과로 바꾸세요. 요청 하나에 작업 하나를 두면 검토할 변경과 재실행할 테스트를 연결하기 쉽습니다.

문제 정의와 구현 계획

첫 요청에서 내 해석과 AI의 해석이 어긋나는 지점을 찾습니다.

아래 과제 명세와 현재 작업 폴더의 진입점·공개 테스트를 확인해줘.
[과제 명세 붙여넣기]

이번 단계에서는 파일 읽기와 현 상태의 테스트 실행까지만 해줘.
요구 동작을 입력 → 기대 출력 → 명세 근거로 정리해줘.
명세에 없는 판단은 가정으로 표시하고, 구현 결과를 바꿀 수 있는 질문만 골라줘.
내가 직접 기대값을 계산할 경계 사례 두 개와 추천 구현 순서를 제안해줘.
범위를 정해 구현 위임

합의한 계약과 테스트 가능한 완료 조건을 붙여 변경을 요청합니다.

[파일:함수]에 [요구 동작]을 구현해줘.
수정 범위는 [파일·함수]이며 기존 함수 시그니처와 공개 테스트는 보존해줘.
[직접 정한 입력]에서 [직접 계산한 기대값]이 나와야 해.
[테스트 명령]을 실행한 뒤 변경 위치, 실제 실행 결과, 실행하지 못한 검증을 알려줘.
명세에 없는 동작을 결정해야 하면 어디가 모호한지 먼저 짚어줘.
실패 재현과 최소 수정

실제 출력과 기대값을 같이 주고, 같은 명령으로 수정 전후를 확인합니다.

[실행 명령]에서 [실제 출력]이 나왔고 기대값은 [기대값]이야.
재현 입력은 [최소 입력]이고 근거는 [명세 문장]이야.
먼저 같은 실패를 재현하고, 값이 달라지기 시작하는 함수나 분기를 짚어줘.
원인에 해당하는 범위만 수정해. 기대값과 재현 입력은 그대로 두고 같은 명령을 다시 실행해줘.
마지막에 전체 테스트 결과와 수정 전후의 차이를 확인해줘.
제출 전 증거 검토

마감 직전에는 코드와 실제로 실행한 검증 결과를 대조합니다.

현재 변경분과 실제 테스트 결과를 읽기 전용으로 검토해줘.
요구사항별로 코드 위치, 확인한 테스트, 남아 있는 검증을 연결해줘.
통과한 테스트가 있어도 해당 규칙을 직접 검사하는지 확인해줘.
중요한 미검증 항목 하나를 골라 최소 입력과 손으로 계산한 기대값을 제안해줘.

게임 전적 집계

매치 식별, 선수별 집계, 승률 계산, 정렬 순서대로 계약을 나누세요. 같은 ID를 다시 봤을 때 이전 승자·패자를 확인할 수 있어야 무해한 재전송과 충돌을 구분할 수 있습니다.

  • 산술 검증. 1승 32경기는 312.5bps이고, 과제 규칙대로 올리면 313bps입니다. 이 기대값으로 파이썬 기본 반올림과 과제 규칙의 차이를 확인하세요.
  • 추가 반례. 62승 103경기와 65승 108경기는 정확한 승률이 다르지만 둘 다 6019bps입니다. 가공한 경기로 이 조건을 만들면, 과제 정렬 규칙에 따라 65승 선수가 62승 선수보다 앞서야 합니다.
  • 설명할 결정. 매치 ID마다 승자·패자를 저장하는 비용과, ID 집합만 저장했을 때 놓치는 충돌을 설명하세요. 반올림을 적용하는 위치도 자신의 코드에서 찾아보세요.
정렬 반례를 검토시키는 프롬프트 
build_leaderboard의 승률 계산과 정렬 기준을 읽기 전용으로 검토해줘.
62승 103경기와 65승 108경기는 둘 다 6019bps이므로 65승 선수가 앞서야 해.
두 선수의 기록을 독립적으로 만들 수 있는 경기 입력을 제안하고, 이 두 선수의 상대 순서를 검사하는 방법을 알려줘.
공개 테스트의 반올림 사례가 이 정렬 규칙까지 검증하는지 확인해줘.

재고 예약

주문 ID의 처리 이력과 남은 재고를 별도의 상태로 적어보세요. 주문별로 같은 SKU의 총수량을 먼저 구한 다음, 전체 품목이 충족되는지를 확인할 지점과 실제 차감할 지점을 정하세요.

  • 직접 계산할 상태 전이. 재고가 board 4개, case 1개일 때 A가 board 2개·board 1개·case 2개를 주문하면 전체 거절입니다. 같은 A로 case 1개만 재요청해도 중복입니다. 이어서 B가 board 4개·case 1개를 요청하면 승인되고 두 품목 모두 0개가 됩니다.
  • 무엇을 검사할지 정하세요. 위 사례의 처리 결과 순서, 최종 재고, 입력 재고와 주문의 보존을 검사하세요. A까지만 실행한 결과도 확인하면 이후 주문의 영향 없이 부분 차감 여부를 볼 수 있습니다.
  • 설명할 결정. 단일 함수 호출에서 품목을 한꺼번에 차감하는 구조와, 여러 요청이 동시에 공유 재고를 읽고 쓰는 상황에서 필요한 제약을 설명하세요. 이 과제는 입력 순서에 따른 처리를 요구합니다.
주문 상태 전이를 검토시키는 프롬프트 
reserve_orders에서 재고를 실제로 차감하는 경로를 읽기 전용으로 검토해줘.
초기 재고는 board 4개, case 1개야.
A의 요청은 board 2개·board 1개·case 2개고, A의 재요청은 case 1개야.
B는 board 4개·case 1개를 주문해. 기대 상태는 insufficient_stock → duplicate → reserved, 재고는 모두 0개야.
첫 A만 처리한 뒤 재고가 그대로인지 확인하는 검사와 전체 시퀀스 검사를 각각 제안해줘.

사후 Q&A와 자가점검

내 답변을 결론 → 코드의 동작 → 실제 확인한 결과 → 보장 범위 순으로 30초 안에 말해보세요. 실행 명령과 관찰 결과는 자신의 기록에서 가져오세요.

예시 질문 · 주문 한 줄이 품절이면 부분 차감을 어떻게 막았나요?

이 구현에서는 주문 수량을 SKU별로 합친 뒤, 모든 품목의 재고를 검사하고 나서 차감합니다. A 주문의 두 번째 SKU가 부족한 사례에서 insufficient_stock과 기존 재고를 확인했습니다. 이 검사는 단일 호출의 순차 처리 범위를 다룹니다.

  • 실행. 과제 진입점에서 전체 테스트를 재현하고 마지막 실행 결과를 보여줄 수 있나요?
  • 검증. 공개 예시 밖에서 기대값을 직접 계산한 사례를 하나 말할 수 있나요?
  • 판단. AI 제안을 채택하거나 바꾼 이유를 명세 문장이나 테스트 결과로 설명할 수 있나요?
  • 한계. 내 구현이 의존하는 가정 하나와 그 가정이 깨지는 입력이나 환경을 말할 수 있나요?
