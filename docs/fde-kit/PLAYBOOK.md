| 11/19 목 | 게임 빌드 릴리스 점검 · 225분 구현 + 5문항 × 3분 | 인터뷰, 사용자와의 성공 조건, 동작하는 화면, 반례, 재시작 기록이 있다. 답변은 AI 도움 없이 직접 쓴다. |

목요일 전체 리허설 시간을 확보하기 어렵다면 75분 모드로 두 과제를 각각 진행하세요. 두 번 모두 맨 마지막에 사후 확인 질문까지 풀어 개발에만 시간을 쓰는 습관을 점검하세요. 금요일은 중간에 드러난 결함을 고치고 재실행할 만큼의 분량으로 마무리하세요.

## 첫 10분 · 제한된 환경에서 시작

1. `pwd`, `ls`, `git status --short`로 작업 위치와 시작 파일을 확인합니다.
2. 루트 README와 실행 명령을 읽고, 시험 환경이 제공하는 런타임 버전과 현재 테스트 상태를 확인합니다.
3. 실무자에게 최근 실제 실패 사례를 묻습니다. 그 사람이 지금 사용하는 자료, 이 결정의 담당자, 걸리는 시간, 성공을 관찰할 위치를 확인합니다.
4. 이미 요구가 상세하면 README를 바탕으로 성공 조건을 제시하고 충돌, 우선순위, 누락된 처리 규칙만 질문합니다.
5. 합의 후부터는 회신할 사용자 경로를 하나 정해 샘플 입력에서 화면과 검증 명령까지 먼저 연결합니다.

## 225분 모드의 작업 지점

- **0–25분** · 최근 실패와 그 영향, 데이터 원천, 목표/기준값/측정법, 시연 범위를 합의합니다.
- **25–45분** · 현재 파일을 파악하고 한 명령으로 작동하는 첫 화면을 보여줍니다.
- **45–130분** · 합의한 경로 하나를 끝까지 구현합니다. 중간에 실무자에게 입력 하나와 관찰값을 보여주고 우선순위 조정을 기록합니다.
- **130–180분** · 잘못된 판정을 내리기 쉬운 반례를 직접 만듭니다. 구현을 설명하기 어려우면 해당 함수의 입력·출력을 먼저 손으로 추적합니다.
- **180–205분** · 한 번 작업을 중단해 인수인계를 써봅니다. 새 세션은 문서와 실제 변경을 읽은 뒤 동일한 서버/테스트를 실행해 상태를 재현합니다.
- **205–225분** · 제출할 코드와 파일을 확인하고, 명령 한 줄로 확인할 수 있는 증거와 남아 있는 제약을 남깁니다.
- **이후 15분** · AI 답변을 열지 않은 채 질문 다섯 개를 각각 3분 안에 답합니다. 첫 문장에 결론, 중간에 코드·관찰, 마지막에 다음 검증을 씁니다.

## 두 번의 연습을 비교하는 방법

각 항목을 0점(근거 없음), 1점(부분 근거), 2점(독립적으로 재현 가능)으로 평가합니다. 이 점수는 두 연습을 비교하기 위한 자가점검입니다.

| 관점 | 2점을 주려면 |
| --- | --- |
| 기술 | 실행 가능한 진입점, 핵심 사용자 경로, 재현 가능한 실패 경로를 확인했다. |
| 의도 | 조건을 입력과 기대값으로 바꿨고, 새 증거로 AI 요청이나 우선순위를 수정한 이유를 기록했다. |
| 인지 | 구현의 코드 위치, 선택한 이유, 관찰 결과, 실패 범위와 다음 검사를 설명할 수 있다. |
| 소통 | 실무자가 합의를 확인했고, 새 세션이 인수인계의 첫 명령으로 실제 상태를 재현했다. |

리허설 후에는 가장 낮은 두 항목 각각에 대해 다음 리허설에서 할 행동 하나를 정하세요. 예를 들어 “품절 케이스를 검증한다”를 “수정 전후에 같은 입력으로 보호할 재고 값을 확인한다”로 구체화합니다.
